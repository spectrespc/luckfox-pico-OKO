# Skill `oko-docs`

Workflow для задач, где нужны `STRUCTURE.md`, `INIT_ORDER.md`, `TESTBENCH.md`.
Роутер и обязательные правила — в `AGENTS.md`; здесь детали.

## 1. Классификация задачи

| Тип задачи | Обязательные документы | Что проверить в репозитории |
|---|---|---|
| Навигация, «где лежит X», выбор места правки | `STRUCTURE.md` (Корневые папки, Ключевые вложенные папки, Корневые файлы) | `ls` нужной папки |
| Активная плата, BoardConfig, сборка образа | `INIT_ORDER.md` §1, §2; `README_RU.md` (Сборка) | `readlink -f .BoardConfig.mk`, `grep -n` по `.mk` |
| U-Boot, ядро, DTS, cmdline, оверлеи | `INIT_ORDER.md` §1–§2, §8 | `project/cfg/BoardConfig_IPC/overlay/...`, DTS в `sysdrv/source/kernel/arch/arm/boot/dts/` |
| Init-скрипты, inittab, порядок S* | `INIT_ORDER.md` §3–§5 | `project/build.sh`, `sysdrv/source/buildroot/.../busybox/inittab` |
| Модули ядра, `insmod_ko.sh`, motor | `INIT_ORDER.md` §6–§7 | `sysdrv/drv_ko/insmod_ko.sh`, `sysdrv/cfg/package.mk`, `RK_ENABLE_MOTOR` |
| `rkipc`, IQ-файлы, `rkipc.ini` | `INIT_ORDER.md` §5, §7 | `project/app/rkipc/.../RkLunch.sh`, `/oem`, `/userdata` |
| Железо, serial, сеть, прошивка, netboot | `TESTBENCH.md` §1–§8 | `netboot-catch.py` (`CMDS`), `start.sh`, `docker-compose.yml` |
| Диагностика после загрузки | `TESTBENCH.md` §8–§9 | `lsmod`, `/proc/rkisp-vir0`, логи |
| Обновление доков | тот док, который затронут, + `CHANGELOG.md` | источник изменения |

Если задача затрагивает несколько областей — бери объединение строк таблицы.

## 2. Алгоритм чтения документа

1. Определи затронутый документ по таблице выше.
2. Получи оглавление: `grep -n '^#' <файл>`.
3. Прочитай только нужный раздел (номера разделов указаны в `AGENTS.md` §2).
4. В ответы пользователю не копируй содержимое дока. Субагенту доки не передаются
   вообще — ни путь, ни номер раздела: в самодостаточный промпт идёт только выжимка
   нужных фактов и пути к исходникам.
5. Факты из дока считай гипотезой до сверки (п. 3).

## 3. Сверка с источниками

Минимальный набор проверок по областям:

```sh
# активная конфигурация
readlink -f .BoardConfig.mk

# ключевые параметры платы (RK_CHIP, RK_BOOT_MEDIUM, RK_ENABLE_MOTOR и т.п.)
grep -nE 'RK_(CHIP|BOOT_MEDIUM|KERNEL_DTS|ENABLE_MOTOR|ENABLE_WIFI|APP_TYPE)' \
  "$(readlink -f .BoardConfig.mk)"

# фактический порядок модулей
grep -n '__insmod\|insmod_wifi' sysdrv/drv_ko/insmod_ko.sh

# фактический список init-скриптов (output/ может устареть)
ls output/out/rootfs_uclibc_rv1106/etc/init.d/S??* 2>/dev/null

# наличие условных модулей в артефакте
ls output/out/oem/usr/ko/ 2>/dev/null | grep -E 'motor|hpmcu'

# сетевые параметры стенда
grep -n '192\.168\.52\|CMDS' netboot-catch.py
```

Правило приоритета: **скрипты, `.mk` и исходники важнее документа**. `output/` —
артефакт сборки, его отсутствие или расхождение само по себе не доказывает ошибку дока;
помечай проверку как «не проверено», если артефакта нет.

## 4. Процедура обновления

1. Внеси изменение в код/конфигурацию.
2. Обнови затронутый раздел документа: только по существу, без переписывания
   неотносящегося текста; стиль и язык — как в файле.
3. В `TESTBENCH.md` обнови «Дату обновления» в §1 (формат `ГГГГ-ММ-ДД`).
4. Добавь запись в `CHANGELOG.md` → `[Не выпущено]` в подходящую категорию
   (`Добавлено`, `Изменено`, `Исправлено`, `Удалено`, `Устарело`, `Безопасность`).
5. Проверь согласованность: упоминания IP, путей, имён модулей и скриптов должны
   совпадать во всех доках и в коде.

## 5. Запреты

- Не редактировать `README.md`, `README_CN.md`, `UPDATE_LOG.md`, `UPDATE_LOG_CN.md` —
  вендорский архив.
- Не считать `output/` и `IMAGE/` источником истины: `IMAGE/` содержит релиз под
  RV1103 Pico Mini и не соответствует активной плате.
- Не передавать субагентам пути и номера разделов доков, а также имена skills
  (`oko-docs` и другие): только самодостаточная выжимка фактов.
- Не копировать большие фрагменты доков в ответы.
- Не менять глобальную конфигурацию `~/.config/kilo/`.
- Не создавать проектные override-агенты `.kilo/agent/*.md` без явного запроса.

## 6. Связанные инструменты

- `/bench` — инжектит `TESTBENCH.md` и задаёт порядок работы со стендом.
- `/docs-check` — автоматическая сверка трёх доков с репозиторием и отчёт о расхождениях.
- `AGENTS.md` §5 — правила делегирования субагентам: самодостаточный промпт с выжимкой
  фактов, без путей к докам и имён skills.
