# CHANGELOG

## [Не выпущено]

Разбор KI-075 продолжен на стенде 2026-11-22. Приложение и версия загрузчика
не менялись (2.3.2 / 1.1.0): опытные сборки `1.1.1`–`1.1.4` не подтвердились
и откачены.

### Изменено
- `docs/BOOTLOADER.md`: убран устаревший тезис «word programming … runs from
  flash without a RAM copy. Erase is per 64-byte block» — теперь явно
  сказано, что слово программируется из Flash (проверено), а стирание
  блока исполняется 67-байтовой RAM-заглушкой (`src/boot/erase_stub.asm`) и на
  стендовом экземпляре не завершается (KI-075). Таблица протокола дополнена:
  ответы `0x11`–`0x13` — `[status][эхо команды]` (2 байта). Размеры образа
  приведены к текущим: загрузчик 2528 Б из 2560, приложение 5359 Б из 5616.

### Проверено на стенде (2026-11-22)
- E0: ожидание `FLASH_IAPSR.PUL` после ключей `PUKR` (boot `1.1.1`,
  2550 Б) — `0x11` принимается, ответа на чтение нет, `SCL hold`, блок не
  стёрт.
- E1: `FLASH_CR1.HALT` (boot `1.1.2`, 2536 Б) и `HALT+AHALT` (boot `1.1.3`,
  2544 Б) в RAM-трамплине — тот же отказ.
- Диагностическая сборка `1.1.4` (заглушка без ожидания `EOP`, сэмпл `IAPSR`
  через ~250 мкс) не ответила: управление не возвращается из записи-триггера,
  то есть самотируемое стирание не завершается.
- Сверка с PM0051 §4.2, SPL (`FLASH_EraseBlock`/`FLASH_Unlock`) и
  AN2659/AN2737 недостающего шага не выявила; подробности и снимки —
  `research/stm8-iap-an2659/`. Все правки откачены, `boot: 2528 bytes
  (last 0x89DF, limit 0x89FF)`.
- Артефакты: `output/bench/stm8/ki075-pul-experiment-20261122.txt`,
  `ki075-cr1-experiment-20261122.txt`.

## [Загрузчик 1.1.0] — 2026-11-21

Разбор KI-075 (I2C-обновление «проходило» без записи Flash). Приложение и
версия тестовой сборки не менялись (2.3.2); меняется только загрузчик и
хост-утилита.

### Исправлено
- **Стирание блока больше не выполняется из Flash.** Контроллер на время
  стирания не обслуживает выборку команд, поэтому цикл ожидания из Flash
  зависал и МК сбрасывался по IWDG. Стирание вынесено в RAM-заглушку
  (`src/boot/erase_stub.asm`, копируется в RAM при старте): положение
  подтверждено живой заглушкой, поведение — как требует SPL
  («block operation must run from RAM»).
- **EOP сбрасывается перед каждой операцией.** Флаг «конец операции»
  «липкий»: старая проверка видела его от прошлой операции и не ждала
  завершения стирания/программирования.
- **Отказ Flash больше не маскируется.** `WR_PG_DIS` и таймаут возвращаются
  как `BOOT_ST_FLASH_ERR`; раньше `boot_flash_write/erase` возвращали
  `BOOT_ST_OK` независимо от результата.
- **Ответ на write-команды — два байта:** `[status][эхо команды]`. Хост
  сверяет эхо, поэтому не может принять устаревший статус за успех
  (именно так обновление печатало `PROGRESS 100` без записи).
- `oko-motor flash`: расхождение версии после прошивки и отсутствие запуска
  приложения теперь ошибка (`RC=1`) с явным сообщением, а не warning.
- `Makefile.stm8`: `BOARD ?= test` — основная линия STM8 собирается по
  умолчанию; продуктовая карта (`BOARD=oko`, 2.2.0) — явная сборка.
  README и `docs/HARDWARE_TESTBOARD.md` обновлены.

### Проверено на стенде (2026-11-21)
- Стендовый STM8S003F3P6: IAP-стирание блока не завершается ни из Flash, ни
  из RAM, ни с байтовым, ни со словесным триггером; при выключенном IWDG
  контроллер молчит >16 с. Word-программирование и SWIM/ICP работают.
  Вывод: дефект экземпляра (второй — неработающий AWU, KI-077), обновление
  по I2C на этой плате невозможно, обход — ST-Link/SWIM.
- `oko-motor flash` на этом экземпляре теперь завершается `RC=1` с
  сообщением «bootloader did not complete command 0x11…».

## [2.3.2] — 2026-11-21

Тестовая плата `BOARD=test` — **2.3.2** и теперь **основная линия сборки**
(`make -f Makefile.stm8 all` без аргументов); продуктовая `BOARD=oko`
остаётся **2.2.0** и собирается явно (код общий; сон по умолчанию включён
только на основной/тестовой сборке).

Стендовая проверка 2.3.0 (T8) выявила дефект сна: после входа в Active-halt
контроллер через ~0,5 с сбрасывался по IWDG — RAM-состояние терялось,
счётчики `GET_SLEEP` всегда 0, в `dmesg` DUT повторялись
`rk3x-i2c ... SCL hold by slave`. Причина: узел AWU на стендовом
STM8S003F3P6 не считает (`AWUEN/TBR/APR` читаются и пишутся, `AWUF` не
выставляется даже через MSR-измерение LSI), поэтому HALT нечем разбудить.

### Изменено
- **Сон по тишине I2C переведён с Active-halt+AWU на Wait mode (`WFI`).**
  Ядро просыпается каждую 1 мс по TIM4 (обработчик кормит IWDG), I2C-slave
  отвечает штатно, такт ядра между тиками снят. `system_ticks` и все тиковые
  таймауты (включая 2-секундный self-reset I2C) работают как в Run mode;
  исчезли SCL-hold таймауты при обращении к спящему контроллеру.
- `GET_SLEEP` 0x0A: байт 2 теперь отдаёт гранулярность пробуждения в
  миллисекундах (1 = тик TIM4) вместо единиц по 10 мс; байт 7 — счётчик
  таймерных пробуждений (`w_timer`, saturating) вместо AWU.  Хосты,
  обновляющиеся до 2.3.2, должны переключить единицы.
- `entries` считается по эпизодам сна (один на период тишины), а не по
  слайсам; `w_i2c` — кадры, пришедшие во сне.  Эпизод закрывается и кадр
  учитывается наверху главного цикла (`sleep_note_frames`), поэтому кадр,
  пришедший между двумя `WFI`, больше не «теряется» и счётчики не занижают
  значения в реальном трафике.
- `oko-motor sleep show` печатает `slice <N> ms` и `wake i2c N timer N`.
- `tests/hardware_test.sh`: `FW_VERSION` (по умолчанию 2.3.2) вместо
  жёсткого 2.3.0, статусы сравниваются по коду протокола (0 IDLE/1 RUNNING/
  2 ERROR), команды `motorctl` повторяются (первый кадр после HALT может
  быть отвергнут), чтение счётчиков сна с ретраями, разбор метки `timer`.
  Секция 12 требует остановленного divinus (его опрос ~2 с короче порога
  3 с, иначе сон не наступает).

### Проверено на стенде (2026-11-21)
- `tests/hardware_test.sh` (`BUS=3 ADDR=0x60`, soak 1800 с): 41 PASS / 0 FAIL,
  12.4 `entries=103 i2c=103 timer=255`, 12.6 `entries 104→105`, 100 циклов
  пробуждения без отказов, позиция стабильна под WDT со сном, `dmesg` без
  новых `SCL hold`.
- Первичная прошивка: ST-Link/SWIM `factory-2.3.2.ihx` + `stm8flash -R`
  (без явного `-R` ядро остаётся остановленным и не отвечает по I2C).
- Обновление по I2C (`oko-motor flash`) на этой плате воспроизводит KI-075
  (PROGRESS 100/RC=0, версия не меняется) — к изменениям сна не относится.

## [2.2.0] — 2026-11-19

Продуктовая сборка — **2.2.0** (`BOARD=oko`), тестовая плата — **2.3.0**
(`BOARD=test`): тот же код, другая карта пинов, а сон включён по умолчанию
только на тестовой плате (`-DSLEEP_DEFAULT_ON=1`).

### Добавлено
- **Сон по тишине I2C (Active-halt + AWU).** После 3 с без обращений к
  `0x60` (порог меняется командой) приложение уходит в цепочку слайсов
  Active-halt; I2C-адрес и AWU будят ядро, `main` кормит IWDG на каждом
  пробуждении. Слайс — `(APR+1)<<(TBR-1) = 25*2048 = 51200` периодов LSI
  (400 мс при 128 кГц), это 80 % окна IWDG `250*256`; отношение не зависит
  от разброса LSI. TIM4 перед HALT останавливается и `SR1.UIF` сбрасывается
  (таймерный wake с STM8S невозможен — datasheet STM8S003F3, Table 11).
  Перед первым слайсом позиции принудительно сохраняются в EEPROM, но не во
  время RUNNING. LED гаснет на время сна. `system_ticks` во сне не идёт,
  поэтому 2-секундный self-reset I2C замирает вместе с тиками.
- Чистая логика решения `src/motor/sleep_logic.h` (макросы, без регистров) и
  хост-тест `tests/test_sleep_logic.c`: тишина, RUNNING, грязный EEPROM,
  незавершённая транзакция, выключенный режим и переполнение 32-битного тика.
- Команды `0x0A GET_SLEEP` (8 байт: режим, состояние, слайс/10 мс, резерв,
  входы BE, пробуждения I2C, пробуждения AWU) и `0x0B SET_SLEEP`
  (`[cmd][mode][idle_s]`, 0 — дефолт 3 с; ответа нет, проверка чтением).
- `oko-motor sleep on|off [S]` и `sleep show` с проверкой версии 2.2.0+ и
  readback; `flash`/`verify` выключают сон перед `ENTER_BOOT`.
- `i2c_host`: ретрай фазы записи (`I2C_WRITE_RETRIES=2`) — первый кадр после
  пробуждения может получить NACK из-за задержки старта HSI; повторяется
  только отказ фазы адреса, частичный кадр не переигрывается.

### Изменено
- Диагностика: `GET_SLEEP` отдаёт saturating-счётчики входов
  (`g_sleep_entries`, `g_wake_by_i2c`, `g_wake_by_awu`) и текущее состояние
  (0 бодрствует, 1 сохраняет EEPROM, 2 взведён, 3 спит).
- `tests/hardware_test.sh`: версия 2.3.0, новая секция 12 (сон/пробуждение,
  100 циклов пробуждения, счётчики, движение после пробуждения, 30-минутный
  soak по монотонности счётчиков), секция сброса стала 13.
- `docs/PROTOCOL*`, `docs/HARDWARE*`, `docs/HARDWARE_TESTBOARD.md`: команды,
  раздел энергосбережения, версия тестовой платы.

## [2.1.1] — 2026-11-07

### Добавлено
- Вариант сборки `BOARD=test` для тестовой платы на STM8S003F3P6:
  `make -f Makefile.stm8 clean all BOARD=test` добавляет `-DBOARD_TEST`,
  выбирает вторую карту пинов (`src/motor/stepper.c`,
  `src/hal/hw_config.c`, `src/boot/boot_hw.c`) и версию **2.1.1**;
  продуктовая сборка по умолчанию остаётся 2.0.2. Смена `BOARD`
  отслеживается маркером `build/.board` и автоматически перекомпилирует
  все исходники, поэтому смешанной сборки не возникает.
- Команда `0x09 SET_POS` (`[cmd][motor][int32 BE]`): принудительно задаёт
  логическую позицию без движения; применяется только в IDLE/ERROR, в
  RUNNING игнорируется, помечает позицию для сохранения в EEPROM.
  Версия прошивки поднята до **2.0.2** (продукт) и **2.1.1** (тестовая
  плата); хосты обязаны проверять версию, потому что неизвестные команды
  игнорируются без NACK.
- `oko-motor`: `set-pos MOTOR VALUE` (с проверкой readback) и
  `home MOTOR [SPEED]` — прижатие к отрицательному упору чанками и
  обнуление через `SET_POS`; имена моторов `focus`/`zoom` в аргументах.

> Известный дефект (KI-042): после движения ниже нуля `GET_POS` отдаёт
> испорченный старший байт (`-1` → `0xFBFFFFFF`), хотя мотор проходит
> заданное число шагов. `SET_POS` и положительные позиции корректны;
> `home` обнуляет шкалу, не читая отрицательную позицию.
- `FLASH_DEV ?= stm8s003f3` для целей `flash`/`verify` (фактический чип обеих
  плат — STM8S003F3P6; сборка и SPL остаются на регистрах STM8S103).
- `docs/HARDWARE_TESTBOARD.md` — карта тестовой платы, электрика
  (5 В, 125 мА/обмотка), скорости 300–400 шаг/с, сборка `BOARD=test` и
  первичная прошивка ST-Link.
- `oko-motor check FILE [X.Y.Z]`: необязательный второй аргумент сверяет
  версию из заголовка OKO8 с ожидаемой (из имени файла в `/api/flash`);
  несовпадение — сообщение в stderr и код возврата 2.
- `Makefile.stm8` берёт версию из `src/core/main.h` и кладёт её в имена
  `app-<версия>.ihx`, `factory-<версия>.ihx`, `app-<версия>.bin`;
  безымянные `app.ihx`/`factory.ihx`/`app.bin` остаются копиями для
  ST-Link-процедур.

### Исправлено
- Ложный `STATUS_ERROR` по nFAULT при первом шаге после пробуждения
  драйвера: `stepper_tick()` теперь опрашивает nFAULT после выдержки
  `wake_ticks` (DRV8833 в окне tWAKE может держать nFAULT низким). На стенде
  до правки обрывалось 3 из 20 реверсов, после — 0 ошибок на 40 движениях и
  чистом sweep 100–800 шаг/с.
- `src/core/main.h`: `APP_VERSION_*` обёрнуты в `#ifndef`, поэтому Makefile
  может задать версию варианта через `-D` без ошибки redefinition.
- `src/motor/eeprom.h`: `EEPROM_SIZE` 1024 → 128 (у STM8S003F3P6 128 Б
  EEPROM); в рантайме константа не используется, прошивка пишет 10 Б.

## [2.0.1] — 2026-11-06

### Добавлено
- I2C-загрузчик OKO: слот `0x8000–0x89FF` (2412 Б), заголовок `0x8A00`,
  приложение `0x8A10–0x9FFF` (4279 Б); команды `0x10–0x14`
  (`BOOT_INFO`/`ERASE`/`WRITE`/`FINISH`/`RESET`).
- Общая команда `0x08 GET_STATE`: `[role, major, minor, patch]` в приложении
  и загрузчике; `0x07` — вход в загрузчик.

  `boot-reset`, паузы перед чтением статуса стирания/записи/финиша,
  корректный разбор отрицательных шагов.

### Исправлено
- Порядок инициализации I2C в загрузчике (`PE` до `ACK`) — без него загрузчик
  не отвечал на `0x60`.
- IWDG перезагружается в циклах стирания и записи; длинная операция больше не
  приводит к сбросу.
- `info` в загрузчике больше не принимает статус `06 00 00` за версию
  `6.0.0` (используется роль из `0x08`).


## [2.0.0] — 2026-10-17
### Изменено
- Двигатели управляются двумя DRV8833 прямой коммутацией обмоток (full-step,
  обе обмотки под током) вместо внешних STEP/DIR-драйверов
- Генерация шагов перенесена из TIM1 в TIM4 ISR: DDA с базой 1000 (1 кГц),
  1–5000 шагов/с; TIM1 больше не инициализируется и его обработчик удалён
- Новая распиновка TSSOP20 (PB0–PB3 на этом корпусе отсутствуют):
  - Focus: PC3/PC4=AIN1/2, PC5/PC6=BIN1/2, PD3=nSLEEP, PD2=nFAULT
  - Zoom: PD5/PD6=AIN1/2, PA3=BIN1, PC7=BIN2, PA1=nSLEEP, PA2=nFAULT
  - PD1 оставлен свободным для SWIM
- Команда calibrate (0x07) и концевые выключатели удалены полностью
- Версия прошивки: 2.0.0

### Добавлено
- Мониторинг nFAULT раз в 1 мс: при аварии (overcurrent/thermal/UVLO) обмотки
  обесточиваются, драйвер переводится в sleep, состояние → ERROR
- `src/motor/stepper_logic.h` — чистые функции DDA/фаз/ограничения скорости,
  общие для прошивки и host-тестов
- `tests/test_stepper_logic.c` — тесты DDA, таблицы фаз и границ скорости

### Исправлено
- Управление nSLEEP: драйвер активен только во время движения (обмотки
  обесточены в покое), что также безопаснее при прошивке через SWIM
- После включения nSLEEP первый шаг выдаётся только через 1 мс, чтобы выходы
  DRV8833 успели активироваться (tWAKE) и первые шаги не терялись
